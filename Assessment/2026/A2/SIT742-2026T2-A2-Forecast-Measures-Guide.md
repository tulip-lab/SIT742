# SIT742 2026T2 Assignment 2 Forecast Measures Guide

This guide explains the two required forecast-performance measures for Assignment 2: MASE and MAPE. It also explains MAE because destination-level MAE is the forecast-error numerator used to calculate MASE. Use this guide as the practical reference for measure definitions, required table inputs, worked examples, missing-value handling, zero-actual handling, and validation-measure calculations in your notebook.

This guide accompanies the [A2 Specification](SIT742-2026T2-A2-Specification.md). For Q1-Q3 function input/output examples, use the [A2 Function Examples Guide](SIT742-2026T2-A2-Function-Examples.md).

## 1. Why A2 Uses Two Performance Measures

Assignment 2 uses two required forecast-performance measures:

- MASE: Mean Absolute Scaled Error.
- MAPE: Mean Absolute Percentage Error.

Both measures are important. They answer different questions:

| Measure | Main question answered | Why it matters in A2 |
| --- | --- | --- |
| MASE | How large is the forecast error compared with typical historical one-step movement for that destination? | Helps compare destinations with different demand scales. |
| MAPE | How large is the forecast error as a percentage of actual demand? | Helps communicate error in an intuitive percentage form. |

Lower MASE is better. Lower MAPE is better.

You should report both measures in:

- Q3, where you implement `evaluate_forecast_wide(...)`;
- Part I integrated evidence, where you compare `naive_lag1` and `naive_lag12`;
- Q4, where you compare validation forecasts and select a model;
- Q5, where final forecast performance is assessed by the teaching-team evaluator;
- Q6, where you discuss measure behaviour and selected-market forecasts.

MAE (Mean Absolute Error) is a supporting calculation in A2. It reports error in the original units of a destination series and is the numerator used in MASE. Destination-level output from `evaluate_forecast_wide(...)` therefore includes `mae`, but MAE does not replace the required MASE and MAPE evidence.

Performance bands and thresholds are not published.

### Reproducible and Stable Measure Evidence

MASE and MAPE evidence should be reproducible from the submitted notebook, visible forecast tables, visible validation actual/result tables, and the relevant training actual history. Do not report hand-edited measure values that cannot be regenerated by running your code.

For stable measure evidence:

- use the same aligned forecast and actual/result rows for the relevant evaluation period;
- use the correct cutoff history for the MASE denominator;
- keep destination-level MASE and MAPE separately identifiable;
- document missing, nonfinite, zero-actual, and unavailable-denominator cases rather than silently replacing them with zero;
- make any stochastic modelling workflow stable enough that rerunning the notebook gives the same final forecast CSV or a clearly justified controlled variation;
- export the final forecast CSV directly from `forecast_submission_wide` and do not manually edit the CSV after export.

## 2. Tables Used By MAE, MASE, And MAPE

MAE, MASE, and MAPE compare a forecast table with an actual/result table. MASE also needs a training actual table to calculate its scaling denominator.

For validation, students can see the actual/result values. For final assessment-period evaluation, the teaching-team evaluator compares the submitted forecast CSV with assessment-period actual/result values, which are not provided to students.

The required final forecast object is:

```python
forecast_submission_wide
```

It must use wide format:

```text
Date, Australia, Japan, ..., <remaining destination columns>
2023M08, <forecast>, <forecast>, ...
2023M09, <forecast>, <forecast>, ...
...
2024M07, <forecast>, <forecast>, ...
```

For each destination, the measure calculation uses:

| Input table | Used by MAE? | Used by MASE? | Used by MAPE? | Purpose |
| --- | --- | --- | --- | --- |
| Forecast table | yes | yes | yes | Forecast values being evaluated. |
| Actual/result table | yes | yes | yes | Actual values for the evaluated months. |
| Training actual table | no | yes | no | MASE denominator only. It measures typical historical movement before the cutoff. |

All tables must be aligned by `Date` and destination column before calculating measures.

## 3. MAE: Forecast Error In Original Units

For one destination, Mean Absolute Error (MAE) is the mean of the absolute differences between actual and forecast values:

```text
absolute_error_t = |actual_t - forecast_t|

MAE = mean(absolute_error_t) over all valid evaluated rows
```

For example, if two aligned rows have actual values `110` and `130`, and forecasts `100` and `100`:

```text
absolute errors = |110 - 100|, |130 - 100| = 10, 30
n = 2
MAE = mean(10, 30) = (10 + 30) / 2 = 20
```

Interpretation: the forecasts have an absolute error of 20 units per evaluated month on average. MAE has the same unit as the destination series. It is not a percentage and it is not scaled.

Calculate MAE separately for each destination:

1. Align forecast and actual/result rows by `Date`.
2. Keep rows where both values are numeric and finite.
3. Calculate one absolute error for each valid row.
4. Set `n` to the number of valid rows.
5. Set `mae` to the mean of those absolute errors.

Do not treat missing or nonfinite values as zero. If `n=0`, return `NaN` or another clear unavailable value for `mae`.

In A2, the destination-level output fields have these meanings:

| Field | Meaning |
| --- | --- |
| `n` | Number of valid aligned forecast-actual rows used for MAE and the MASE numerator. |
| `mae` | Mean absolute forecast error across those `n` rows, in the destination series' original units. |

The same destination-level `mae` value becomes the MASE numerator:

```text
MASE = MAE / MASE denominator
```

MAE is scale-dependent. The same numerical MAE can represent different relative difficulty for destinations with different historical movement. For this reason, A2 uses MASE and MAPE as the required cross-destination performance measures and does not require an aggregate `mean_mae`.

## 4. MASE: Scaled Error Measure

MASE evaluates forecast error after scaling it by the destination's historical movement.

```text
MASE = mean_absolute_forecast_error / mean_absolute_training_one_step_change
```

where:

```text
mean_absolute_forecast_error =
mean(|actual_t - forecast_t|) over the evaluated forecast period

mean_absolute_training_one_step_change =
mean(|training_actual_t - training_actual_{t-1}|) over all valid lag-1 pairs in the training period available up to the cutoff
```

For validation MASE:

- the numerator uses validation actual values for `2023M03` to `2023M07`;
- the denominator uses only training actual values available up to `2023M02`.

For final assessment-period MASE:

- the numerator uses assessment-period actual/result values for `2023M08` to `2024M07`, which are not provided to students;
- the denominator uses only public historical actual values available up to `2023M07`.

Official MASE uses `naive_lag=1` unless the specification explicitly says otherwise. A `lag=12` naive forecast is a useful baseline comparison, but it does not change the official MASE denominator.

Before computing the MASE denominator:

1. Sort the training actual table chronologically by `Date`.
2. Use all valid lag-1 pairs available up to the cutoff.
3. Do not restrict the denominator to the same number of months as the forecast horizon.
4. Do not fill missing denominator values with zero.

Destination-level MASE output should include at least:

```text
mase
denominator
n_denominator_pairs
mase_available
denominator_warning
```

## 5. MAPE: Percentage Error Measure

MAPE evaluates forecast error as a percentage of actual demand.

```text
MAPE = mean(|actual_t - forecast_t| / |actual_t|) * 100
```

MAPE uses the forecast table and the actual/result table only. It does not use the MASE training denominator.

MAPE must be calculated on evaluated rows where:

- the actual value is numeric and finite;
- the forecast value is numeric and finite;
- the actual value is not zero.

If the actual value is zero, percentage error is undefined. Do not divide by zero. Exclude zero-actual rows from the MAPE calculation and report when this affects availability or row counts.

Destination-level MAPE output should include at least:

```text
mape
n
```

In the required destination-level table, `n` is the number of valid forecast-actual rows used for MAE and the MASE numerator. MAPE uses the subset of those rows where the actual value is nonzero. If zero actuals cause MAPE to use fewer rows, report or discuss that difference clearly; a separate field such as `n_mape` may be used.

## 7. Worked Example: MAE And MASE For One Destination

First calculate MAE from the aligned validation actual and forecast values:

```text
|110 - 100| = 10
|130 - 100| = 30
|125 - 100| = 25
|140 - 100| = 40
|150 - 100| = 50

forecast MAE = mean(10, 30, 25, 40, 50) = 31
```

Here, `n=5` and `mae=31`. This means that the forecast differs from the actual value by 31 units per validation month on average.

Next calculate the MASE denominator from the training actuals:

```text
|90 - 80| = 10
|95 - 90| = 5
|105 - 95| = 10
|100 - 105| = 5

training one-step denominator = mean(10, 5, 10, 5) = 7.5
```

Finally calculate MASE:

```text
MASE = 31 / 7.5 = 4.13
```

Interpretation: a MASE of 4.13 means the average forecast error is 4.13 times the average one-step month-to-month movement in the training history.

## 8. Worked Example: MAPE For One Destination

This section calculates MAPE only. The MASE denominator is not used.

Calculate the percentage error for each evaluated row:

```text
|110 - 100| / 110 * 100 = 9.09%
|130 - 100| / 130 * 100 = 23.08%
|125 - 100| / 125 * 100 = 20.00%
|140 - 100| / 140 * 100 = 28.57%
|150 - 100| / 150 * 100 = 33.33%
```

Then average the percentage errors:

```text
MAPE = mean(9.09, 23.08, 20.00, 28.57, 33.33) = 22.81%
```

Interpretation: a MAPE of 22.81% means the average absolute forecast error is about 22.81% of the actual demand values in the evaluated rows.

## 9. Wide-Table Example: MAE, MASE, And MAPE By Destination

Suppose your validation forecast table is:

| Date | Australia | Japan |
| --- | ---: | ---: |
| `2023M03` | `100` | `200` |
| `2023M04` | `100` | `220` |

The validation actual/result table is:

| Date | Australia | Japan |
| --- | ---: | ---: |
| `2023M03` | `110` | `190` |
| `2023M04` | `130` | `250` |

The training actual table up to `2023M02` is:

| Date | Australia | Japan |
| --- | ---: | ---: |
| `2022M12` | `95` | `180` |
| `2023M01` | `105` | `210` |
| `2023M02` | `100` | `200` |

For Australia:

```text
forecast errors = |110 - 100|, |130 - 100| = 10, 30
n = 2
MAE = mean(10, 30) = 20 original units per month

MASE denominator = mean(|105 - 95|, |100 - 105|) = mean(10, 5) = 7.5
MASE = 20 / 7.5 = 2.67

MAPE = mean(10 / 110, 30 / 130) * 100 = 16.08%
```

For Japan:

```text
forecast errors = |190 - 200|, |250 - 220| = 10, 30
n = 2
MAE = mean(10, 30) = 20 original units per month

MASE denominator = mean(|210 - 180|, |200 - 210|) = mean(30, 10) = 20
MASE = 20 / 20 = 1.00

MAPE = mean(10 / 190, 30 / 250) * 100 = 8.63%
```

The destination-level output should clearly show MAE and both required performance measures:

| destination | mae | mase | mape | denominator | n_denominator_pairs | mase_available | denominator_warning | n |
| --- | ---: | ---: | ---: | ---: | ---: | --- | --- | ---: |
| Australia | 20.00 | 2.67 | 16.08 | 7.50 | 2 | `True` | `False` | 2 |
| Japan | 20.00 | 1.00 | 8.63 | 20.00 | 2 | `True` | `False` | 2 |

The equal MAE values do not imply equal relative performance. Australia's `mae=20` is 2.67 times its typical training movement, while Japan's `mae=20` is 1.00 times its typical training movement. This is why MASE helps compare forecast performance across destinations.

## 10. Aggregating MASE And MAPE Across Destinations

Assignment 2 has 20 destination series. Calculate destination-level measures first, then aggregate.

For this two-destination toy example:

```text
mean_mase = mean(20 / 7.5, 20 / 20) = 1.83
mean_mape = mean(16.08, 8.63) = 12.36%
```

Calculate aggregate measures from the unrounded destination-level values, then round only for display.

For the real assignment:

```text
all_20_mase = mean(destination_mase values across the 20 destinations where MASE is available)
all_20_mape = mean(destination_mape values across the 20 destinations where MAPE is available)
```

Each destination receives equal weight in the aggregate unless the specification later states otherwise. Aggregate measures should be computed as unweighted summaries of destination-level measures unless otherwise stated.

For example, `mean_mase` is the mean of destination-level MASE values and `mean_mape` is the mean of destination-level MAPE values. Do not pool all destination-month rows first unless you clearly label the result as a different aggregation.

MAE remains visible at destination level as the MASE numerator. Do not calculate `mean_mae` as a substitute for `mean_mase` or `mean_mape`.

## 11. Baseline Forecasts Versus Measure Calculations

There are two separate ideas:

- baseline forecast model;
- forecast-performance measure.

Baseline model:

```text
forecast for a future month = value from a selected lag in the available history
```

For `lag=1`, the baseline uses the most recent previous month. Under a fixed-cutoff multi-step horizon, this often becomes a recursive carry-forward baseline. For example, if the cutoff value is `2023M02 = 100`, validation baseline forecasts for `2023M03` to `2023M07` may all be `100` unless your group uses and clearly justifies another non-leaking design.

For `lag=12`, the baseline uses the same month from the previous year when available.

The baseline model is not the same thing as the MASE denominator. A `lag=12` forecast is a baseline model. It does not change the official MASE denominator.

When evaluating both `naive_lag1` and `naive_lag12` baseline forecasts in `baseline_validation_comparison`, use:

```python
evaluate_forecast_wide(..., naive_lag=1)
```

unless the specification explicitly states otherwise.

The `lag` column describes how the forecast was generated. The `naive_lag` argument describes the MASE denominator used for evaluation.

MAPE does not use a naive-lag denominator. It uses actual/result values in the evaluated rows.

## 12. Missing Values, Zero Actuals, And Unavailable Measures

Use practical and transparent rules.

For forecast-error rows used by MAE, MASE, and MAPE:

- use rows where actual and forecast values are numeric and finite;
- report `n`, the number of rows used for MAE and the MASE numerator;
- do not treat missing actual or forecast values as zero.

For MASE denominator rows:

- sort the training actual table chronologically by `Date`;
- use only valid lagged pairs where both training values are numeric and finite;
- report `n_denominator_pairs`;
- do not fill missing denominator values with zero;
- if there are no valid denominator pairs, or the denominator is zero, return `NaN` or a clear unavailable flag for MASE.

For MAPE rows:

- exclude rows where the actual value is zero;
- do not divide by zero;
- if there are no valid nonzero actual rows, return `NaN` or a clear unavailable flag for MAPE.

Toy MASE denominator example:

```text
Training actuals:
2022M10 = 80
2022M11 = missing
2022M12 = 95
2023M01 = 105
2023M02 = 100

For naive_lag=1, possible pairs are:
2022M11 - 2022M10: invalid because 2022M11 is missing
2022M12 - 2022M11: invalid because 2022M11 is missing
2023M01 - 2022M12: |105 - 95| = 10
2023M02 - 2023M01: |100 - 105| = 5

MASE denominator = mean(10, 5) = 7.5
n_denominator_pairs = 2
```

## 13. Recommended Python Pseudocode

This is pseudocode, not a complete evaluator.

In this pseudocode, `sort_by_month_label(...)` should sort with a real year-month representation such as `pandas.Period(..., freq="M")`, not ambiguous lexicographic string sorting.

```python
def evaluate_forecast_wide(
    forecast_wide_df,
    actual_wide_df,
    training_actual_wide_df,
    start_month,
    end_month,
    required_destinations=None,
    naive_lag=1,
    date_column="Date",
):
    if required_destinations is None:
        required_destinations = [
            column for column in forecast_wide_df.columns if column != date_column
        ]

    aligned_forecast, aligned_actual = align_by_date_and_destination(
        forecast_wide_df,
        actual_wide_df,
        start_month,
        end_month,
        required_destinations,
        date_column,
    )

    destination_metric_rows = []
    training_actual_wide_df = sort_by_month_label(training_actual_wide_df, date_column)

    for destination in required_destinations:
        forecast = to_numeric_array(aligned_forecast[destination])
        actual = to_numeric_array(aligned_actual[destination])
        training_actual = to_numeric_array(training_actual_wide_df[destination])

        valid_error_rows = rows_where_actual_and_forecast_are_finite
        errors = actual[valid_error_rows] - forecast[valid_error_rows]
        n = count(valid_error_rows)
        if n == 0:
            mae = NaN
        else:
            mae = mean(abs(errors))
        valid_mape_rows = rows_where_actual_and_forecast_are_finite_and_actual_is_nonzero
        mape_errors = actual[valid_mape_rows] - forecast[valid_mape_rows]
        n_mape = count(valid_mape_rows)
        if n_mape == 0:
            mape = NaN
            mape_available = False
        else:
            mape = mean(abs(mape_errors / actual[valid_mape_rows])) * 100
            mape_available = True

        # MASE denominator: use all valid lagged pairs in the supplied
        # training history, not only a window matching the forecast horizon.
        left = training_actual[naive_lag:]
        right = training_actual[:-naive_lag]

        valid_denominator_pairs = rows_where_left_and_right_are_finite
        diffs = left[valid_denominator_pairs] - right[valid_denominator_pairs]
        denominator = mean(abs(diffs))
        n_denominator_pairs = len(diffs)

        if (
            n == 0
            or mae is missing
            or n_denominator_pairs == 0
            or denominator <= 0
            or denominator is missing
        ):
            mase = NaN
            denominator_warning = True
            mase_available = False
        else:
            mase = mae / denominator
            denominator_warning = False
            mase_available = True

        destination_metric_rows.append({
            "destination": destination,
            "n": n,
            "mae": mae,
            "mase": mase,
            "mape": mape,
            "denominator": denominator,
            "n_denominator_pairs": n_denominator_pairs,
            "mase_available": mase_available,
            "denominator_warning": denominator_warning,
        })

    destination_metrics = pandas.DataFrame(
        destination_metric_rows,
        columns=[
            "destination",
            "n",
            "mae",
            "mase",
            "mape",
            "denominator",
            "n_denominator_pairs",
            "mase_available",
            "denominator_warning",
        ],
    )
    aggregate_metrics = summarise_destination_metrics(destination_metrics)

    return destination_metrics, aggregate_metrics
```

The assignment function must return the two objects as the tuple shown above. `destination_metrics` is a pandas DataFrame with the displayed column order. `aggregate_metrics` is a Python dictionary containing, in order, `n_destinations`, `mean_mase`, `median_mase`, and `mean_mape`. Variables such as `n_mape` or `mape_available` may be used internally, but they are not additional required output fields.

## 14. Common Mistakes

Before submitting, check that you are not:

- using the GitHub page URL in `read_csv` instead of a raw CSV URL;
- reporting only one required forecast measure when both MASE and MAPE are required;
- treating MAE as a substitute for required MASE and MAPE evidence;
- calculating MAE as the sum of absolute errors instead of their mean;
- reporting MAE as a percentage or as a unit-free value even though it remains in the destination series' original units;
- pooling destination-month rows before calculating destination-level MAE;
- mixing destinations together before computing destination-level MASE or MAPE;
- computing MASE on misaligned forecast and actual/result tables;
- computing MAPE on misaligned forecast and actual/result tables;
- using validation actuals or assessment-period actual/result values in the MASE denominator;
- using assessment-period actual/result values in your forecast workflow;
- using `lag=12` as the official MASE denominator;
- restricting the MASE denominator to the forecast-horizon length when the specification asks for all valid training lagged pairs;
- dividing by zero when calculating MAPE;
- treating missing evaluation values as zero;
- submitting a final CSV with `model_label` or diagnostic columns;
- submitting a final CSV in the wrong table shape;
- manually editing reported performance measures or the final forecast CSV after code export;
- leaving stochastic model results uncontrolled so that the final forecast table changes unpredictably between runs.
